## 1. 分担の考え方（一言）

| 観点 | Type-B を使う会社 | Type-A を使う会社 |
|------|-------------------|------------------------|
| **ビジネス上の優先** | ブランド・既存顧客・**既存システムとの連続性** | 新規獲得・**変化への適応速度**・多言語・デジタル体験 |
| **技術的優先** | 変更範囲の最小化、**コアを守る** | スケールと仕様変更に強い **サーバーレス** |
| **AIの置き方** | 表に出すより **裏側の防衛・運用補助** | **対話型オーケストレーション**として前面 |

## 2. Type-B を選ぶ会社向け設計

**想定例:** 歴史・格式、既存会員基盤、基幹（予約・決済）を大きく変えたくないホテルグループ、規制・監査で「変更の説明責任」が重い組織。

### 2.1 アーキテクチャの要点

- **フロント／基幹**は従来型（例: ALB 後段アプリ、RDS）を維持する前提。
- **生成 AI / LLM** は、ゲスト向けチャネルの主役ではなく、**セキュリティ・監視・インシデント対応**（Sentinel 系）に寄せる。
- ネットワークは **VPC 内の明確な層**（公開 / アプリ / DB / （任意）LLM サブネット）。
- 本人確認は **Cognito + MFA** など、既存アイデンティティ戦略と揃えやすい構成。

### 2.2 このリポジトリでの配置

| 領域 | Terraform / コード |
|------|----------------------|
| メイン IaC | `terraform/type-b` |
| Lambda（Type-B） | `lambda/type-b/*`（chatbot / sentinel 等） |

### 2.3 運用・ガバナンス上のフォーカス

- 変更は **インフラの差分が読みやすい単位**（巨大 `main.tf` の分割は継続改善）。
- 本番は **リモート state・ロック** を前提にした `apply` 運用。
- 監査: WAF / CloudTrail / ログの保持・暗号化を既存設計に合わせる。

## 3. Type-A を選ぶ会社向け設計

**想定例:** インバウンド・デジタルネイティブ向け、**チャット／自然言語**で予約導線を短くしたい、**サーバ運用を抑えたい**ブランド。

### 3.1 アーキテクチャの要点

- **API・データ**はサーバーレス寄り（Lambda + DynamoDB 等）。
- **Amazon Bedrock Agent** で予約読み書き・案内をオーケストレーション。
- ネットワークは **VPC エンドポイント** 寄りで、プライベート接続とガバナンス（フロー、KMS、WAF）を重視。
- フロントは **S3 + CloudFront + Cognito** など、静的配信とトークン認可。

### 3.2 このリポジトリでの配置

| 領域 | Terraform / コード |
|------|----------------------|
| メイン IaC | `terraform/type-a` |
| Lambda（Type-A） | `interface`, `tools/reader`, `execution/reservation`（[`STRUCTURE.md`](../STRUCTURE.md)） |

### 3.3 運用・ガバナンス上のフォーカス

- Bedrock Agent の **準備（prepare）** など、**手元 CLI に依存する処理**は CI ロールに寄せると監査しやすい。
- エイリアス ID は **環境変数または変数** で明示し、循環依存を避ける（現構成の意図）。
- 依存ライブラリは **Dependabot / 脆弱性ワークフロー** とセットで見る。

## 4. 両社種に共通して「社内専用」に置くもの

情シス・開発基盤・監査用の **顧客予約スタックとは別 state** を推奨。

| 用途 | Terraform |
|------|-----------|
| 社内 VPC・Session Manager 向け VPCE・社内 S3 | `terraform/corp-internal` |

Type-B 企業でも Type-A 企業でも、**社内ネットワークと本番予約系は分離**するのが安全です。

**補足:** 社内向けの **Type-B（Enterprise）/ Type-A（Cloud-Native）比較・Terraform 骨子・Lambda スタブ**は `internal-infra/README.md` と `internal-infra/terraform/` を参照してください。`terraform/corp-internal` は引き続き「最小共通の社内 VPCE」用として使えます。

## 5. 意思決定の早見表（どちらを選ぶか）

**Type-B が向く条件（例）**

- 既存 RS や連携システムの **API 契約・改修コスト**が高い。
- 「AI に予約データを直接触らせる」ことへの **コンプライアンス上の慎重さ**が強い。
- 組織が **ウォーターフォールに近く、リリース頻度が低い**。

**Type-A が向く条件（例）**

- 新規ブランド・**グローバル展開**で、チャット／多言語が主導線。
- **スモールチーム**でインフラ運用を極小化したい。
- データが DynamoDB 前提の **イベント駆動・スケール**に収まる。
